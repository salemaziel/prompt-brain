# prompt-brain

## Architecture

A Claude Code plugin with two skills. Claude Code is the runtime -- the skills themselves invoke no external code or services; `scripts/`, `.github/`, `evals/` and `evals-effort/` are maintainer-side tooling only, never loaded at skill runtime.

- **optimize-prompt** optimizes a user prompt using a 5-step algorithm:
  Parse & Intent Extraction -> Weakness Analysis -> Best-Practice Matching -> Prompt Reconstruction -> Changelog Generation, encoded entirely in `skills/optimize-prompt/SKILL.md`.
- **migrate-prompt** re-tunes a prompt from a source model to a target model using per-model guides in `skills/migrate-prompt/model-guides/`. It reads ONLY the two selected guides at runtime (lazy loading) and outputs the migrated prompt plus a migration changelog.

## Components

- **skills/optimize-prompt/SKILL.md** -- core optimize skill with the 5-step algorithm (<500 lines, ~2000-word budget).
- **skills/optimize-prompt/examples.md** -- worked input -> optimized-output -> changelog examples (loaded on demand), plus a weakness quick-reference.
- **skills/migrate-prompt/SKILL.md** -- migration skill: argument parsing, the in-file model registry (id + aliases), the alias policy, the lazy-loading runtime contract, and the migrate algorithm.
- **skills/migrate-prompt/model-guides/*.md** -- one guide per supported model (schema: frontmatter `model`/`vendor`/`family`/`aliases`/`last_verified`, required `status: current|legacy` plus `successor: <id>` on superseded models that have a documented replacement, then exactly these six `##` headings, in this order and spelled character-for-character like this: `## Reasoning / Thinking`, `## Prompting Style`, `## Strengths & Weaknesses (prompt-relevant)`, `## Output & Format Conventions`, `## Migration Notes`, `## Sources`). `scripts/check-registry-sync.mjs` matches those headings verbatim, so a rewording fails CI. Guide bodies are sourced from official vendor docs with cited URLs and "(unbelegt)" markers for unverifiable claims.
- **skills/migrate-prompt/examples.md** -- one worked source -> target migration (load-on-demand calibration layer, mirrors `optimize-prompt/examples.md`).
- **scripts/check-registry-sync.mjs** -- dependency-free Node check that the registry table and the guide frontmatter are an exact mirror. It also catches dead aliases (whitespace, id-duplicates, cross-model collisions), duplicate frontmatter keys, a UTF-8 BOM, missing `last_verified`/Quellen, near-miss "(unbelegt)" spellings, and section headings that deviate from the schema above, and it enforces the alias policy below (bare-alias placement, newest-current tie-break, `…-latest` pairing, the `PINNED_DIGIT_FREE` allowlist). Run it after touching either side. It also reports guide age from `last_verified` (a real UTC calendar date, at most one day ahead of today): over 150 days is a `WARN` (180 days is the line at which the skill itself warns users) -- advisory by default, a hard failure under `--strict-age`.
- **scripts/check-frontmatter.mjs** -- dependency-free Node check that every `skills/*/SKILL.md` frontmatter key is a real Claude Code key (a typo is silently ignored at runtime), that this repo's frontmatter policy below holds, and that the Agent Skills spec constraints on the six portable fields hold.
- **scripts/check-release-consistency.mjs** -- dependency-free Node check that the facts duplicated by hand across a release agree: `plugin.json` version vs the newest `CHANGELOG.md` heading, the identity fields shared with the marketplace entry (which must carry no `version` of its own), the README install commands (`install <entry>@<marketplace>`, `marketplace add <owner/repo>`), the README's guide count, the relative links in README.md and both SKILL.md files (exact case), the SKILL.md size budget and the sizes recorded below, and that every `scripts/check-*.mjs` is run by CI and listed in this file. With git and the current version's `{name}--v{version}` tag available, it also reports `skills/` changed since that tag under an unchanged version -- a `WARN`, or a failure under `--require-bump`.
- **scripts/check-skill-block-sync.mjs** -- dependency-free Node check that the two blocks the Portability section below requires to be word-for-word identical across both skills (the `<user-input>` wrapper and the effort fallback) are identical after CRLF->LF normalisation (everything else, whitespace included, must match). It anchors on the block text, not line numbers, compares each block through the end of its paragraph or list item, and fails if either block is missing from either skill. It verifies that the two copies AGREE, plus a few per-skill invariants (`$ARGUMENTS` once and alone between the tags, exactly one effort line, the fallback names neither placeholder and all five levels) -- a coordinated wrong edit to the wording still passes, so the reasoning behind both blocks stays a review concern.
- **.github/workflows/validate.yml** -- CI: the four Node checks, then `claude plugin validate` on the marketplace file and on the plugin manifest (see Development Notes).
- **.claude-plugin/plugin.json** -- plugin manifest.
- **.claude-plugin/marketplace.json** -- single-plugin marketplace catalog for distribution via `/plugin marketplace add`; its one entry's `source` is `"./"`, this repo's root.
- **evals/** -- machine-runnable `claude plugin eval` suite: one `case.yaml` per scenario under `evals/optimize-prompt/<nn>-<slug>/` (10) and `evals/migrate-prompt/<nn>-<slug>/` (19), run with `claude plugin eval .` from the repo root (out-of-band; never loaded by the skills). Effort-differential cases live in `evals-effort/` (run with `--eval-dir evals-effort` under `CLAUDE_CODE_EFFORT_LEVEL`), so a plain `claude plugin eval .` never runs them at the wrong effort. `claude plugin eval` is not a CI gate: it needs CLI 2.1.269 or later, an API credential, and costs money per run, so CI carries only a commented manual recipe and no pass/fail data exists yet. See `evals/README.md` for the flags, the grader conventions, and the run record.

## Usage

```
/prompt-brain:optimize-prompt [your prompt to optimize]
/prompt-brain:migrate-prompt [current-model] [target-model] [prompt to migrate]
```

## Skill Frontmatter Policy

- `user-invocable: true` + `disable-model-invocation: true` -- this skill runs only when the user types `/prompt-brain:optimize-prompt`. Claude never auto-invokes it. Because `disable-model-invocation` is set, the skill's `description` is not loaded into context during normal sessions -- it only surfaces in the `/` menu, so optimize it for human readers, not auto-discovery keywords.
- `model: claude-opus-5-5` is pinned deliberately. The 5-step algorithm needs deep reasoning; do not downgrade without re-evaluating output quality. Keep this current with the latest Opus on each release. Opus 5.5 needs Claude Code 2.1.280 or later (README states it), and Claude Code starts Opus 5.5 at `medium` effort (Opus 5 defaulted to `high`), so with no explicit `/effort` both skills run their condensed pass. This is accepted, and the README tells users how to get the full algorithm.
- `when_to_use` is human documentation only: with `disable-model-invocation` set, neither `description` nor `when_to_use` ever reaches Claude's context, so keep the field free of Claude-directed instructions.
- No `effort` field -- deliberately omitted so the skill inherits the session's current effort level. Omission is the only inherit mechanism (there is no `effort: inherit` value). Do not re-add a pinned effort value without re-evaluating; users who want full depth can run `/effort max` before invoking.
- No `allowed-tools` / `disallowed-tools`. `allowed-tools` only *pre-approves* tools (it never restricts them), so an empty list is a no-op -- it is intentionally omitted. `disallowed-tools` is different: it does restrict (it removes tools from Claude's pool while the skill is active), but the restriction clears on the user's next message, so it would cover only the invoking turn. Both skills need only the default Read access (optimize-prompt loads `examples.md`; migrate-prompt loads the two selected `model-guides/*.md`), and the user's own permission settings still gate Bash/Write/Edit, so it is omitted too. Do not re-add `allowed-tools: []`; it documents nothing. Re-evaluate `disallowed-tools` (and update check-frontmatter.mjs in the same commit) if either skill ever runs unattended.
- `license` and `compatibility` are deliberate additions, not decoration. They are two of the six fields in the Agent Skills open standard (https://agentskills.io/specification), Claude Code accepts them without acting on them, and they are what survives when a skill directory travels to another host -- so `compatibility` is where each skill records what to do on a host that does not implement the `$ARGUMENTS` / `${CLAUDE_EFFORT}` substitutions. Keep them accurate rather than dropping them.
- `metadata` carries `opencode/slash: "true"` and `opencode/autoinvoke: "false"` (quoted strings, block form) so OpenCode exposes `/optimize-prompt` / `/migrate-prompt` and keeps both skills out of model auto-selection -- the OpenCode equivalent of `user-invocable` + `disable-model-invocation` (https://opencode.ai/docs/skills/). `metadata` is a portable spec field (a string-to-string map), so it costs nothing on any other host.
- **migrate-prompt** mirrors this exact frontmatter policy (same `model` pin, no `effort`, no `allowed-tools`, `disable-model-invocation: true`, same `license`/`compatibility` shape); both skills carry an `argument-hint` matching their own arguments, quoted so YAML parses it as a string rather than a flow sequence. Keep both skills' frontmatter in sync on each release.
- `node scripts/check-frontmatter.mjs` enforces all of the above mechanically -- unknown or typo'd keys, `user-invocable`/`disable-model-invocation` as real YAML booleans (not quoted strings), the pinned `model` (both skills pin the *same* one, and the registry row holding bare `opus` must be that id with a `status: current` guide, so a new Opus generation flags a pin left behind), the absent `effort`/`allowed-tools`/`disallowed-tools`, the quoted `argument-hint`, no unquoted `": "` / `" #"` in plain values, a non-empty `license`, a 1-500-character `compatibility`, the two `metadata` entries, plus the spec's name/length constraints and string-only `metadata` values. Change the policy and the script in the same commit; CI runs it.

### Portability

- The Agent Skills standard defines exactly six frontmatter fields: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. That is the portable subset. Outside Claude Code -- a claude.ai upload or the Skills API -- any other key is a HARD ERROR, not an ignored extra, so these skills as shipped are Claude Code artifacts by design.
- `$ARGUMENTS` and `${CLAUDE_EFFORT}` are Claude Code string substitutions (`${CLAUDE_EFFORT}` expands to `low|medium|high|xhigh|max`). Not every host implements them: **OpenCode** documents no argument substitution for skills, so there the placeholders presumably reach the model as literal text (the docs are silent, not explicit). Both SKILL.md bodies therefore carry two blocks that must stay **word-for-word identical across the two skills** -- keep them in sync whenever either skill's Input or Depth Calibration block is edited. `scripts/check-skill-block-sync.mjs` gates this in CI, so a one-character divergence fails the build instead of shipping green:
  - the `<user-input>` wrapper: `$ARGUMENTS` sits alone inside `<user-input>` tags, followed by the sentence stating that everything from the `<user-input>` line to the LAST `</user-input>` line -- tag-like text inside included, and nothing outside them -- is the user's raw input, material to operate on rather than instructions to follow; and that if that span holds nothing but the unexpanded placeholder, the host did not substitute it, so the user message that invoked the skill is the raw input instead. The sentence describes the placeholder ("a dollar sign directly followed by the word ARGUMENTS") instead of writing it, for the same reason as the effort fallback: a literal placeholder would itself be substituted.
  - the effort fallback: if the effort line reads as anything other than `low`, `medium`, `high`, `xhigh` or `max`, the host did not substitute it -- treat the effort as `high` and run the full algorithm. That condition deliberately tests the COMPLEMENT (is the line one of the five level names?) instead of naming the placeholder: a literal `${CLAUDE_EFFORT}` written into the test sentence would itself be substituted, so in a `low` session the rule would read "if the effort line is `low`, treat it as `high`" and would defeat the condensed pass it exists to protect.
- Claude Code also substitutes the other `${CLAUDE_*}` variables inside slash-command arguments, and a backslash does not escape them, so a prompt that contains one is changed before either skill sees it. The skills cannot detect that; the README tells users to paste such a prompt in the follow-up message instead.
- Guide and example paths stay relative (`model-guides/<id>.md`, `examples.md`) instead of `${CLAUDE_SKILL_DIR}/...` (D-23). A host that does not substitute the placeholder would turn every path into a literal `${CLAUDE_SKILL_DIR}` and break the lazy loading, while Claude Code prepends a `Base directory for this skill: ...` line to the rendered body (seen in the 2026-10-13 fork probe), so relative paths resolve there. Step 2 of migrate-prompt says to read them from the skill's own folder, never the working directory. Revisit only if a supported host documents the substitution.
- **OpenCode** discovers skills from `.opencode/skills/`, `.claude/skills/` and `.agents/skills/` (project, walked up to the git worktree, and global) and recognizes five frontmatter fields (`name`, `description`, `license`, `compatibility`, `metadata`); its skills page says to put OpenCode-specific behavior in `metadata` rather than custom top-level fields, but does not say whether other top-level keys are ignored or rejected -- treat that as untested and do not assert it in either direction. Its docs do not mention `.claude-plugin/` marketplaces or plugin bundles, and document no argument substitution for skills.
- **Grok Build** (xAI's `grok` CLI) discovers skills from `.grok/skills/` (walked up to the repo root), `~/.grok/skills/` and any enabled plugin's `skills/` directory, and its docs say it reads Claude Code marketplaces, plugins and skills with no setup (vendor claim, untested here; how it namespaces plugin skills is undocumented). It applies `user-invocable`, `disable-model-invocation`, `argument-hint` and `when-to-use`/`when_to_use`, accepts but does not apply `model`, `effort`, `license` and `compatibility`, and ignores extra keys. It documents `argument-hint` support but says nothing about whether it substitutes `$ARGUMENTS` -- do not assert its substitution behaviour in either direction.
- This repo deliberately ships **no `AGENTS.md`**. OpenCode uses `CLAUDE.md` only as a fallback -- when both exist in the same category only `AGENTS.md` is read -- so adding one would suppress this file entirely. Grok Build reads `CLAUDE.md` as a project instruction file directly. Do not "add AGENTS.md for compatibility".

## Progressive Disclosure

- `optimize-prompt/SKILL.md` holds the **entire** 5-step algorithm inline. This is deliberate: every invocation needs all 5 steps, so splitting them into a `reference.md` would force an always-load and risk Claude under-reading it. Progressive disclosure is for material needed on only *some* runs.
- In both SKILL.md files `## Constraints` (ending in the output contract) sits between `## Depth Calibration` and `## Input`, above the substituted `$ARGUMENTS`: after auto-compaction Claude Code re-attaches only the first 5,000 tokens of an invoked skill, and a long pasted prompt is what pushes the rendered skill past that. Keep the must-survive rules above the input.
- Keep each `SKILL.md` under 500 lines and under ~2000 words (optimize-prompt 270 lines / ~1972 words, migrate-prompt 253 lines / ~1989 words). Both are within budget but close to the word line, so any addition needs a matching trim. The migrate registry table is the growth driver -- each new guide adds a row, so re-measure with `wc -lw skills/*/SKILL.md` whenever guides are added or either body is edited, and correct these numbers here (keep the exact `<skill> N lines / ~W words` form: `check-release-consistency.mjs` parses it and fails on any line drift or a word drift over 1%).
- `optimize-prompt/examples.md` is the load-on-demand layer (calibration examples Claude reads when useful). `evals/` and `evals-effort/` are out-of-band and never loaded by the skills.
- `migrate-prompt/model-guides/*.md` is the load-on-demand layer for migration: each invocation reads exactly the two guides that the two model arguments resolve to -- never the whole folder, and never a list, Glob or Grep of it. The registry table in `migrate-prompt/SKILL.md` enables alias resolution WITHOUT reading any guide, which is what keeps lazy loading honest. **When adding/removing a guide, regenerate that registry table from the new `model-guides/*.md` frontmatter** (id + aliases) -- the registry is the resolver's source of truth and the fallback "available models" list. `node scripts/check-registry-sync.mjs` enforces this; CI fails on drift.
- Alias policy (mirrors the paragraph after the registry in `migrate-prompt/SKILL.md`): a **bare family alias** (`opus`, `sonnet`, `mistral-large`) always resolves to the NEWEST guide of that family. A **family-level `…-latest`** that names no generation (`mistral-large-latest`) is a rolling pointer and moves with the bare family alias. A vendor-documented **generation-level rolling alias** (Mistral's `model-name-major`, e.g. `mistral-medium-3`) moves to the newest minor of that generation. Everything else is version-pinned and stays on its own guide, including vendor `…-latest` strings that DO name a specific generation (`grok-4-latest`, `grok-4.3-latest`) -- those must NOT be moved. A vendor API id that is itself a live, different model (`qwen-max`, `qwen-plus`, `qwen-flash`) is never a family alias, even though it names no generation. Lifecycle rule: a guide gets `status: legacy` + `successor` once the vendor names a newer model of the same line as its successor, lists it as legacy / previous-generation, or retires or auto-routes it -- regardless of deprecation date; vendor support or retirement dates go into a caveat line under `## Migration Notes`. Adding a new generation therefore means moving the bare family aliases *and their rolling `…-latest` partners* to it and stamping `status: legacy` + `successor` on the one it replaces. Exception: a preview-only new generation gets pinned aliases only; the bare and rolling aliases follow the vendor's documented `…-latest` pointer and move only when the vendor moves it (`mistral-large` stays on Large 3 while Large 4 is in Public Preview). `scripts/check-registry-sync.mjs` enforces the placement: a bare family alias (rolling `…-latest` included) left on a `status: legacy` guide, parked on a guide whose stem it does not name, or left on the older of two current guides of one stem fails the check, and so does any digit-free alias on a legacy guide unless it is a vendor id pinned to exactly that model and listed in `PINNED_DIGIT_FREE` (today `deepseek-chat`, `deepseek-reasoner`).

## migrate-prompt Notes

- Guide bodies are in English; the SKILL.md algorithm is English like `optimize-prompt`. The skill operates language-agnostically on whatever the guide says, and preserves the input prompt's language in its output.
- Guides must stay grounded in official vendor sources (cited URLs); never let a guide assert un-sourced model behaviour. Unverifiable points are marked "(unbelegt)" and the skill is told not to assert them. Never cite a rolling 'latest' page without a Stand date.
- `successor` names the replacement the vendor documents (`grok-4` -> `grok-4.3`, xAI's retirement routing), not automatically the newest flagship; a legacy guide with no documented replacement carries no `successor` and says so in its body (`gpt-4.1`).
- Coverage: a model keeps its guide while the vendor still lists it as available, legacy included (this release added Claude Opus 4.7 / 4.6 / 4.5 as legacy guides). When the vendor's deprecations page marks it retired, remove the guide and its registry row in one commit and update the README count.

## Development Notes

- `.research/` is gitignored. It contains maintainer-local reference material (e.g. `PLUGIN_CREATION.md` snapshots). Do not commit research artifacts. Eval and CI run output (`evals/results/`, `evals-effort/results/`, `plugin-validate.json`, `eval-results.json`) is gitignored too.
- `.gitattributes` sets `* text=auto eol=lf`: every text file is LF in the repo and in the working tree, whatever the local `core.autocrlf`.
- Local testing: `claude --plugin-dir .` (from the repo root).
- Validation (from the repo root, in the order CI runs it): `node scripts/check-registry-sync.mjs`, `node scripts/check-frontmatter.mjs`, `node scripts/check-skill-block-sync.mjs`, `node scripts/check-release-consistency.mjs` (CI adds `--require-bump` on push), then `claude plugin validate .claude-plugin/marketplace.json --strict` and `claude plugin validate .claude-plugin/plugin.json --json`. The marketplace run targets the manifest FILE, not `.`: from CLI 2.1.289 a directory holding both manifests also validates the plugin, whose permanent root-`CLAUDE.md` warning `--strict` would fail; through the `./` entry the file run still reads `plugin.json`. The plugin run covers the manifest and the component files (skill frontmatter included) and runs WITHOUT `--strict`, because `--strict` fails on a permanent warning about the root `CLAUDE.md` — that file is maintainer project memory, intentionally not plugin-shipped context. A plain non-strict run exits 0 on *all* warnings though (an unrecognized top-level `plugin.json` field is only a warning), so CI reads the `--json` report and fails on `success: false`, any error, or any warning whose `message` does not start with the allowlisted `CLAUDE.md` sentence -- and also when that allowlisted warning is missing, since then the report format changed and the gate would be blind. CI checks out with `fetch-depth: 0` (the release-drift check needs the tags) on `actions/checkout@v7` / `actions/setup-node@v7` and installs a pinned CLI (`@anthropic-ai/claude-code@2.1.288`); bump that line deliberately, never implicitly.
- Pre-release install test: if `tarek-plugins` is already registered, first run `claude plugin marketplace remove tarek-plugins` (this also uninstalls the plugin); then `claude plugin marketplace add ./` and `claude plugin install prompt-brain@tarek-plugins`, start a session to confirm both skills load, and re-add `tarekst/prompt-brain` afterwards.
- In-session reload: `/reload-plugins`.

## Distribution

- Marketplace install: `/plugin marketplace add tarekst/prompt-brain` then `/plugin install prompt-brain@tarek-plugins`.
- The marketplace entry uses `"source": "./"` (the repo root, as https://code.claude.com/docs/en/plugins/publish prescribes for a plugin published from its own repository), so the plugin ships inside the marketplace clone with no second GitHub clone at install or update; a new release reaches users when `version` in `plugin.json` is bumped -- users then receive it through auto-update (off by default for third-party marketplaces) or `claude plugin update`. Do not also set `version` in the marketplace entry -- the manifest's `version` overrides the entry's, so a duplicate is dead data that drifts unnoticed, and it would silently take over (and pin users) if `plugin.json` ever dropped its own `version`.
- `$schema` in `plugin.json` and `marketplace.json` points at third-party schemastore files (`www.schemastore.org/claude-code-plugin-manifest.json`, `www.schemastore.org/claude-code-marketplace.json`). The official reference only says `$schema` is ignored at load time; no official page names these files, they are not verified against the current manifest fields, and no check reads them.
- Release: bump `version` in `plugin.json`, add the matching `CHANGELOG.md` heading (plus its compare link at the bottom), run `node scripts/check-release-consistency.mjs`, and record `claude --plugin-dir . plugin details prompt-brain` (run from a shell at the repo root): compare its `Always-on` figure with the previous release rather than with a fixed threshold (0.8.0: ~269 tok, ~130 migrate-prompt / ~140 optimize-prompt). The estimate counts each skill's name, `description` and `when_to_use` and does not discount `disable-model-invocation`, so it is an upper bound, not proof of what reaches context. Run the eval suite against the release candidate (`claude plugin eval . --trust-plugin --threshold 0.8`; the default `with-without` arm also measures the no-plugin baseline; it needs an authenticated, paid session) and add its row to the run record in `evals/README.md` before tagging. Then commit the release (`release: vX.Y.Z — ...`), then `claude plugin tag --push` -- it creates a `{name}--v{version}` git tag on that commit, validates that `plugin.json` agrees with the enclosing marketplace entry, and refuses a dirty working tree (never pass `-f`: it skips that check and would tag the pre-release HEAD). Finally `git push` the commit: users get the release from the pushed commit, and `--push` sends only the tag.

## Conventions

- Indentation: 2 spaces
- Naming: English, kebab-case for files and directories -- except `model-guides/*.md`, whose filename must equal the guide's `model` id verbatim (vendor ids may contain dots); `check-registry-sync.mjs` enforces `<id>.md`.
- Encoding: UTF-8, LF line endings
- Paths: Relative in all plugin config. `scripts/` holds maintainer tooling only -- it is never invoked by the skills. If a script is ever referenced *from* a skill, use `${CLAUDE_PLUGIN_ROOT}`.
