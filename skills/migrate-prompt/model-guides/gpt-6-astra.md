# GPT-6 Astra

## Reasoning / Thinking
- `reasoning.effort` accepts `low | medium | high | xhigh | max`. **`none` is not supported** — the value is rejected with HTTP 400. Documentation guidance for migrating users: "When migrating from `minimal`, or from `none` to GPT-6 Astra or GPT-6.1 Sol, start with `low` and compare results."
- A model-specific default effort is not documented (unbelegt) — always set `reasoning.effort` explicitly instead of assuming an inherited value.
- `reasoning.mode`: `standard` (default) | `pro` — according to the reasoning guide, "GPT-5.6 and GPT-6 models support `standard` and `pro` reasoning modes in the Responses API" (documented only for the Responses API). Mode and effort are independent; `pro` performs more model work at higher latency and higher token consumption. `configuration_update` (see below) is documented only in standard mode with a single agent.
- `reasoning.context`: `auto` (default) | `current_turn` | `all_turns` — controls whether reasoning from prior turns is rendered into the next sample; the response reports in the `reasoning.context` field which mode actually took effect. The reasoning guide designates `all_turns` only for GPT-5.6 models and GPT-6.1 Sol; for Astra the value is not documented (unbelegt) — set `auto` and verify the response field.
- `reasoning.summary: "auto"` provides the most detailed available summary (opt-in, summaries appear in the `summary` array of the reasoning output item). Raw chain-of-thought is not visible via the API; reasoning tokens still occupy context and are **billed as output tokens**. `max_output_tokens` caps reasoning + response together; OpenAI recommends initially reserving at least 25,000 tokens for reasoning and output combined.
- New compared to the GPT-5.6 family: Effort can be adjusted **mid-conversation** via `configuration_update` items without rewriting the prompt — depth escalation belongs in orchestration, not in prompt text. Limits per documentation: GPT-6 family only in standard mode (single-agent); two `configuration_update` items cannot appear immediately adjacent (the API rejects this); do not combine with automatic compaction/truncation (`/responses/compact` also rejects such histories — apply a fresh update after explicit compaction); leave request-level `reasoning.effort` unchanged (prompt caching), the response continues to report the request-level value.

## Prompting Style
- OpenAI describes Astra as "stronger at general instruction following" and "better able to follow longer instructions, but can also be more sensitive to information in context". Long, structured instruction blocks are therefore viable — but attached context (files, tool results, skills) exerts a stronger influence than with predecessors.
- **Grant autonomy explicitly.** The model "is more likely to ask the user a question when additional input could materially change the result". Remedy according to documentation: Instruct it to "bias towards action and carry the user's intended task to completion", explicitly declare phrasings like "can you…"/ "help me…" as a direct work assignment, and seek confirmation only after "a concrete, reviewable result".
- **Spell out precedence.** Because Astra responds more sensitively to instructions in skills and other files, the documentation recommends the verbatim sentence: "The user's instructions take precedence over guidelines provided in a skill." Additionally demand transparency — in case of a conflict, the model should name the file and quote the colliding passage. Review accessible files for behavior-shaping instructions prior to migration.
- **Explicitly request prose**, otherwise Astra defaults to lists, tables, and Markdown. Documentation phrasing: "Default to using clear, concise paragraphs, each developing one main idea."
- Documentation style negative list: Actively prohibit "slop words" (e.g., "Bottom Line", "leverage", "it's worth noting"), contrastive framing ("X, not Y"), and invented composite labels.
- **Actively instruct delegation** rather than capping it: Astra tends to delegate too infrequently in multi-agent setups. Recommended prompt building block: "If at any point you can parallelize work by delegating tasks to another agent … you should do so."
- **Calibrate test scope** instead of writing "test thoroughly": "Do not write tests for reversible, low-impact changes", and only expand test scope when "new changes, failures, or unresolved concerns justify it".

## Strengths & Weaknesses (prompt-relevant)
- Strengths: According to documentation, "state-of-the-art performance in computer use, browsing, software engineering, science, and professional work" at lower estimated API cost per task ("Its estimated API cost per task was lower than earlier models despite its higher per-token pricing."); positioned as "our most capable model, built for the hardest end-to-end work" that carries complex tasks "from an initial request to a finished result". Large tool set (`web_search`, `file_search`, `image_generation`, `code_interpreter`, `hosted_shell`, `apply_patch`, `skills`, `computer_use`, `mcp`, `tool_search`), 1.05M context, async tool calling (`async: true` on the function) for parallel reasoning during tool execution, and mid-turn steering via WebSocket, accepting incoming corrections without discarding completed work.
- Weaknesses: Idiosyncrasies that must be compensated for in the prompt: Unnecessary pause-and-clarify cycles ("This can cause it to stop when the user may expect it to make reasonable assumptions"); over-testing on small changes ("For smaller tasks, this can result in broader tests than the task requires"); tendency toward verbose, heavily formatted answers and "recurring phrases across sessions"; heightened sensitivity to instructions in skills/files; too infrequent delegation.
- Operational constraints: No `none` effort, no sampling parameters, tool calling only via the Responses API, and under EU data residency Astra supports neither `service_tier: "fast"` nor `service_tier: "priority"` (select standard processing there). Ultrafast mode (`service_tier: "ultrafast"`, since 2026-09-29) is available only with US data residency or Global Processing; Fast mode for Astra comes without a latency SLA. Requests additionally pass through asynchronous misalignment monitoring.
- Rollout: Released on 2026-09-03; the API documentation (as of 2026-10-13) contains no limited-access notice and documents the model as regularly available. The phased rollout format of the first few days (initially selected organizations, then broader via ChatGPT tiers, API, and cloud partners) is not verified on the retrieved documentation pages (unbelegt) — do not interpret as having been open to all developers on day one.

## Output & Format Conventions
- Context window 1,050,000 tokens, of which max 922,000 input and 128,000 output. Knowledge cutoff: April 30, 2026.
- Pricing: $10 / MTok Input, $50 / MTok Output, Cached Input $1, Cache Writes $12.50. **Price cliff at 272K input tokens**: Above this threshold, 2x input/cache rates and 1.5x output rates apply to the entire request. Batch/Flex 50% of standard rate, Fast mode 2x.
- Endpoints: Chat Completions, Responses, Batch. Unsupported: Realtime, Assistants, Fine-tuning, Embeddings, image generation endpoint, video, audio, Moderation, and legacy completions.
- Features: `streaming`, `structured_outputs`, `function_calling`, `file_search`, `image_input`, `web_search`, `prompt_caching`.
- Prompt caching is configured via `prompt_cache_options.ttl` (e.g. `"30m"`) — `prompt_cache_retention` is the deprecated predecessor.
- Rate limits (Grow tier, highest of the three tiers Build/Launch/Grow since 2026-10-06): 15,000 RPM, 40M TPM, 15B batch queue limit.
- `text.verbosity` (`low` | `medium` | `high`) is usable with Astra: The deployment checklist demonstrates `text: { verbosity: "low" }` on `gpt-6-astra` and terms the parameter "the main lever for balancing brevity against completeness" — set default detail level through it, specify content, structure, and length in the prompt.
- Enforce output formatting contract via **Structured Outputs** or an explicit prose instruction; without either, the response tilts into verbose, list- and table-heavy Markdown.

## Migration Notes
- **MIGRATING FROM gpt-6-astra**: Re-evaluate autonomy, precedence, and prose prompt components — they compensate for Astra idiosyncrasies and become redundant baggage on target models without a question-asking bias. Conversely, re-introduce: Explicit test and verification steps (Astra tests thoroughly without being asked), structure/formatting guidelines if the target model does not format automatically, and delegation **caps** instead of delegation prompts if the target delegates more willingly. Technically: Remove `reasoning.mode`/`reasoning.context`/`configuration_update`, `async: true`, and mid-turn steering; re-introduce sampling parameters (`temperature`, `top_p`) only if supported by target model; rewrite `prompt_cache_options.ttl` to target's caching syntax; shrink context budget from 1.05M to the smaller target window.
- **MIGRATING TO gpt-6-astra**: (1) Set `model` to `gpt-6-astra`. (2) Replace `reasoning.effort: none`/`minimal` with `low` and compare results — a zero-thinking fast path does not exist here. (3) Shift tool calling to the **Responses API**; Chat Completions remains usable otherwise, but does not support tools. (4) Remove `temperature`, `top_p`, `top_logprobs` (and `logprobs` in Chat Completions). (5) `prompt_cache_retention` → `prompt_cache_options.ttl`. (6) Add autonomy building blocks, otherwise the model pauses for clarifying questions. (7) Add precedence rule over skills/files to system prompt and audit bundled files for conflicting directives. (8) Remove legacy "be thorough" / "double-check" instructions carried over from prior models and cap test scope instead. (9) Actively permit delegation instead of capping it. (10) Apply verbosity countermeasures (prose instruction plus slop word ban). (11) Recalibrate `max_output_tokens`, since reasoning tokens count toward it. (12) Audit prompts above 272K input tokens against the price cliff. (13) Under EU data residency, remove `service_tier: "fast"` and `service_tier: "priority"` — neither is supported there; `service_tier: "ultrafast"` is likewise unavailable there (US residency / Global only). (14) An existing `reasoning.mode: "pro"` (e.g. from gpt-5.6-sol) can remain, but is documented only for the Responses API. It is not documented together with `configuration_update`, so choose standard mode there. (15) Carry over an existing `text.verbosity` value (e.g. from gpt-5.6-sol/-terra) and check, according to the deployment checklist, whether blanket "Be concise" lines are still helpful alongside it.
