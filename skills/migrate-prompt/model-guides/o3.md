# o3

## Reasoning / Thinking
- **Type: always on (pure reasoning model).** o3 belongs to the o-series, which internally generates "reasoning tokens" before producing a response; these tokens serve planning, tool usage, and multi-step problem solving. They are **not visible** via the API, are not retained in context between turns, but occupy context window space and are billed as output tokens.
- **Depth control via `reasoning_effort`.** The parameter controls how much the model "thinks". Documented levels: `low` (efficient reasoning with modest latency increase), `medium` (balanced point on the Pareto curve), and `high` ("Hard reasoning, complex debugging, deep planning, and high-value tasks"). Additional values such as `none`, `minimal`, `xhigh` exist depending on the model — which ones o3 specifically supports is not explicitly listed in primary docs **(unbelegt)**.
- **Why traditional chain-of-thought is counterproductive here:** Because o3 executes the reasoning process internally, according to OpenAI it is "unnecessary" to prompt the model with "think step by step" or "explain your reasoning". The o3/o4-mini Prompting Guide also warns that prompts like "plan more extensively" can actually **degrade** performance — the model already reasons natively; additional meta-reasoning instructions are redundant.
- **Context budget:** When experimenting, initially reserve at least ~25,000 tokens for reasoning + output; `max_output_tokens` bounds total generation and prevents truncated responses. Exact reasoning token usage is recorded in the `usage` object under `output_tokens_details`.

## Prompting Style
- **"Less is more."** o3 excels with concise, clear instructions: "Keep prompts simple and direct". Too many constraints or examples can reduce accuracy.
- **Zero-shot first, then few-shot.** Reasoning models often do not need few-shot examples; if used, they must be tightly aligned with instructions.
- **High developer message adherence.** Developer messages are treated as explicit developer directives and function as "durable interface contracts" — they should define clear boundaries (e.g. when a tool should be invoked). Place critical rules at the beginning of the prompt.
- **Prescriptive for complex tasks.** For multi-step workflows, explicitly specify the exact order of function calls and clear boundaries ("when to use a tool vs. answer directly").
- **Use delimiters.** Markdown, XML tags, and section headers help cleanly separate input sections. Provide clear end goals and success criteria.

## Strengths & Weaknesses (prompt-relevant)
- Strengths: o3 is positioned as "a well-rounded and powerful model across domains" and leads in coding, math, science, and visual reasoning (SOTA on Codeforces, SWE-bench, MMMU; SWE-bench Verified 69.1%). Exceptionally strong at image, chart, and diagram analysis. It can combine tools **agentically** (web search, Python data analysis, image understanding, image generation) and autonomously decides on the timing and nature of tool deployment.
- Weaknesses: o3 makes overall **more claims** than o1 — leading to more correct statements, but also more hallucinated statements; in the PersonQA evaluation, this effect is more pronounced than in SimpleQA. Known quirks during tool use: The model occasionally promises future tool calls without executing them, or exhibits "lazy behavior" (terse answers / "no time"). Countermeasures: Start fresh conversations for new topics; discard irrelevant earlier tool calls and summarize instead.

## Output & Format Conventions
- **Developer messages instead of system messages.** Starting with `o1-2024-12-17`, the o-series supports developer messages; system messages sent by developers are automatically converted internally into developer messages.
- **Markdown restrained by default.** To enable Markdown formatting in responses, include `Formatting re-enabled` in the **first line** of the developer message.
- **Modalities:** Image as input (input only); Function Calling, Structured Outputs, and Streaming are "Supported". Context window: 200,000 tokens, max output: 100,000 tokens, knowledge cutoff: June 1, 2024 (snapshot `o3-2025-04-16`).
- **Tool / Function Calling:** Set `strict: true` so schemas are reliably followed; encode "when to call this function" directly in the function description (not only in the developer prompt). In-distribution configurations typically have fewer than ~100 tools and fewer than ~20 arguments per tool. Persist chain-of-thought between tool calls via the Responses API using `include=["reasoning.encrypted_content"]`.

## Migration Notes
- **Deprecation:** `o3-2025-04-16` will be shut down on December 11, 2026 according to the OpenAI deprecations page; official replacement is `gpt-5.6-sol`. New migrations TO o3 should be transitional only. (The o3 model page additionally lists GPT-5 as successor — its snapshot `gpt-5-2025-08-07` is shut down on the same day.)
- **MIGRATING TO o3**: **Remove** explicit "think step by step" / CoT instructions and planning scaffolding from GPT prompts — they are redundant and can degrade performance. Reduce few-shot examples (zero-shot first). System messages become developer messages; prepend `Formatting re-enabled` if Markdown is desired. Plan a reasoning token budget (reserve ≥ ~25,000). Use `reasoning_effort` as a tuning knob, not as the primary quality lever. Keep hallucination risks in mind for fact-heavy tasks (more claims → more potential errors).
- **MIGRATING FROM o3 to a GPT-5.x reasoning successor** (official replacement `gpt-5.6-sol`): Preserve effort controls — on the Responses API `reasoning.effort`, for gpt-5.6-sol `none | low | medium (default) | high | xhigh | max` — and adopt o3's previous level as baseline (extrapolation: GPT-5.6 docs state "preserve your current reasoning effort as the baseline" for migrations from GPT-5.5/5.4). Do **not** add CoT or planning scaffolding: The target is also a reasoning model that expects task, constraints, and output format rather than prescribed intermediate steps. Maintain the developer message contract (tool boundaries, critical rules upfront).
- **MIGRATING FROM o3 to a non-reasoning GPT model** (e.g. `gpt-4.1`, per model page "Smartest non-reasoning model" without a reasoning step): `reasoning_effort` is eliminated; explicit CoT/planning prompting may become necessary again (the GPT-4.1 guide: "GPT-4.1 is not a reasoning model", induce step-by-step planning via prompt). Typical pattern per OpenAI: o-series for planning/decisions, GPT models for execution — many workflows combine both.
