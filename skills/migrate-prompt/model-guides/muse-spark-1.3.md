# Muse Spark 1.3

## Reasoning / Thinking
- Typ: **immer an, nicht abschaltbar**. `reasoning_effort: "none"` wird ausdrücklich abgelehnt („Disables reasoning. Not supported by Muse Wonder or Muse Spark: returns `HTTP 400`") — jeder Zero-Thinking-Schnellpfad aus einem Vorgängermodell muss auf `minimal` oder `low` abgebildet werden.
- Parametername ist protokollabhängig: `reasoning_effort` (Chat Completions) vs. `reasoning.effort` (Responses API). Stufen: `minimal | low | medium | high | xhigh | max`. `max` gibt es in der Spark-Reihe ausschließlich für Standard-Tier-`muse-spark-1.3`, nicht für `muse-spark-1.3-contributor`.
- **Kein publizierter Default-Wert**: Ohne den Parameter „the model still reasons at a model-determined level" — welche Stufe das ist, steht nirgends (unbelegt). Effort deshalb im Prompt-Vertrag immer explizit setzen.
- Chain of Thought ist privat („The model's chain of thought is private. The raw reasoning is not returned as readable text"); auf Chat Completions wird `reasoning_content` für externe Aufrufer zu leer redigiert. Zusammenfassungen gibt es nur auf der Responses API über `reasoning.summary` (`auto` ≈ ein Satz / `concise` / `detailed`) — und auch die sind nicht garantiert.
- Reasoning-Tokens zählen gegen `max_tokens` bzw. `max_output_tokens` und werden zum Output-Satz abgerechnet; ausgewiesen in `completion_tokens_details.reasoning_tokens` bzw. `output_tokens_details.reasoning_tokens`. Bei `xhigh`/`max` Token-Budgets neu bemessen.
- Reasoning über Turns/Tool-Schleifen erhalten: auf der **Responses API** über `previous_response_id` oder `include: ["reasoning.encrypted_content"]`, auf der **Messages API** per Anthropic-`thinking`-Replay (Historie clientseitig; `redacted_thinking` trägt den verschlüsselten Blob und wird zurückgespielt). Nur Chat Completions trägt kein Reasoning über Turns („each turn reasons from scratch").
- Metas eigene Effort-Heuristik: hoher Effort für „proofs and calculations, complex code generation, architecture trade-off analysis", `low` für direkte Antworten mit weniger Latenz und Kosten. `logprobs` wird nicht unterstützt (HTTP 400).

## Prompting-Stil
- **`developer`-Rolle statt `system`**: Meta empfiehlt ausdrücklich „prefer a `developer` message over the `system`" für Ton, Format und Dauerregeln. Bei der Migration die System-Prompt-Schicht entsprechend umetikettieren, nicht nur kopieren.
- **Effort ist Teil des Prompt-Designs**, nicht bloß ein Kostenregler: Für sauber abgegrenzte Aufgaben kann laut Meta `reasoning_effort=xhigh` ein vollständiges Artefakt in einem einzigen Durchlauf liefern — mehrstufige Prompt-Choreografie wird dann überflüssig.
- **Rückfragen einplanen oder unterbinden**: Das Modell „asks for input when needed", hat laut Launch-Blog „better calibration on what constitutes irreversible actions" und „confirms before taking consequential actions". Für unbeaufsichtigte Läufe Autonomie explizit erteilen und Defaults für Unterspezifiziertes vorgeben.
- **Lange, komplexe Instruktionen sind erlaubt**: 1.3 „follows complex, long-form instructions more reliably than earlier Muse Spark models" — vorsorgliches Zerlegen in Mini-Prompts ist nicht nötig.
- **Tool-Beschreibungen tragen die Last**: „Write clear, specific descriptions for the tool and for each parameter. The model uses them to decide when and how to call the tool." Kein Nacherklären der Tools in Prosa im System-Prompt.
- **Prompt-Reihenfolge fürs Caching**: „Put stable content first, such as system prompt, instructions, and examples, and put variable content last." Caching ist automatisch und ohne Setup aktiv, die Reihenfolge entscheidet über die Trefferlänge.

## Stärken & Schwächen (prompt-relevant)
- Einordnung: laut Modellübersicht „the latest version" der Muse-Spark-Reihe und „Recommended for new work", „the default model in the code examples throughout these docs", verfügbar in Muse Code und der Meta Model API. Metas leistungsfähigstes Modell ist laut derselben Seite (Stand 2026-10-13) Muse Wonder (`muse-wonder-1.0`, Preview), das dieselben Requests auf denselben Endpunkten annimmt.
- Stärken: „Trained for long-horizon, agentic workflows" — hält Kontext und Zwischenergebnisse, arbeitet „through messy or conflicting inputs", korrigiert Plan-Lücken proaktiv und bearbeitet mehrere Workflows parallel. Nativ multimodale Wahrnehmung (Bild, Video, Dokumente); Bilder als base64-Data-URL oder öffentliche URL direkt im Message-Content, inklusive Selbstinspektion gerenderter Ergebnisse und Fehler-Screenshots; Computer-Use aus Klartext-Ziel plus Screenshot ohne Koordinatenangaben.
- Token-Ökonomie: gegenüber 1.2 laut Meta rund **20 % weniger Tool-Calls und 25 % weniger Tokens**, „takes fewer turns where not needed and is less verbose" — von 1.2 übernommene „fasse dich kurz"-Instruktionen sind meist redundant.
- „Better awareness of its own capabilities and limitations" und weniger Halluzinationen — defensive „erfinde nichts"-Blöcke lassen sich abspecken. Dazu „stronger adversarial robustness, with improved resistance to adversarial inputs and prompt injections"; Injection-Härtung im Prompt bleibt sinnvoll, ist aber nicht mehr die einzige Verteidigungslinie.
- Schwäche (offiziell dokumentiert): **Audio**. „Audio understanding in Muse Spark 1.3 is currently not fully supported, and response quality for requests including audio content may be degraded. For audio, use Muse Spark 1.2, or Muse Voice Transcribe for dedicated speech-to-text."
- Schwäche: `tool_choice` akzeptiert nur `"auto"` — jede erzwungene Tool-Wahl (`required` oder benannte Funktion) endet in HTTP 400. Tool-Zwang muss sprachlich im Prompt formuliert werden.
- Kein publizierter Knowledge Cutoff und kein publiziertes Output-Token-Limit (unbelegt). Die Benchmark-Vergleiche des Launch-Blogs liegen nur als Grafik vor, ohne Zahlen im Fließtext.

## Output- & Format-Konventionen
- Kontextfenster **1.048.576 Tokens**; Input Text, Bild, Video, Audio (eingeschränkt, s. o.) und PDF, Output ausschließlich Text. Maximale Output-Tokens sind nicht publiziert (unbelegt).
- Structured Output: `response_format` mit `"type": "json_schema"` (Chat Completions) bzw. `text.format` (Responses API); „the model constrains token generation to produce only valid JSON matching your schema". `strict` ist per Default `false`; mit `strict: true` muss die Wurzel ein einfaches Objekt sein, jedes Objekt `additionalProperties: false` setzen und `required` **alle** Keys auflisten. Rekursive Schemas sind nicht unterstützt. Grenzen (gelten auch für Function-Tool-`parameters`, Überschreitung → HTTP 400): Tiefe 10, 5.000 Properties, 120.000 Zeichen gesamt, 1.000 Enum-Werte (Default, pro App anhebbar); String-Enums mit >250 Werten max. 15.000 Zeichen; Schemas mit >200.000 Knoten nach `$ref`-Expansion werden abgelehnt.
- Tool Calling: `parallel_tool_calls` ist per Default `true` (mehrere Calls pro Turn möglich); `max_tool_calls` deckelt nur Built-in-Tools, nicht Function-Tools; Tool-Namen müssen `^[a-zA-Z0-9_.-]+$` mit höchstens einem Punkt erfüllen. Auch mit `strict: true` sind die generierten Argumente nur schema-*geleitet* und „not guaranteed to validate against it" — serverseitig weiter validieren.
- Drei Protokolle gegen dieselben Modelle, dieselbe Auth und denselben Preis: Responses (`/v1/responses`, Metas „recommended default for new work", einzige Route für Search Grounding; Reasoning-Erhalt per Encrypted Replay oder `previous_response_id`), Chat Completions (`/v1/chat/completions`, OpenAI-Format, kein Reasoning-Erhalt über Turns), Messages (`/v1/messages`, Anthropic-Format, Historie clientseitig, Reasoning-Erhalt per `thinking`-Replay; `thinking: {type: "disabled"}` → HTTP 400, `output_config.effort` reicht nur `low`–`xhigh` durch).
- Preise pro 1M Tokens: Standard $1.25 Input / $0.15 Cached Input / $4.25 Output; Contributor $0.10 / $0.002 / $0.20 — der Contributor-Tarif erkauft den Preis mit „permission to use your prompts and completions to train future Meta models". Kein Batch-Rabatt und keine Preisstaffel nach Kontextlänge dokumentiert.
- Prompt-Caching ist automatisch; Treffer stehen in `usage.prompt_tokens_details.cached_tokens` (Chat Completions) bzw. `usage.input_tokens_details.cached_tokens` (Responses). Auf der Responses API lässt sich mit `prompt_cache_retention: "24h"` verlängerte Vorhaltung bis 24 Stunden anfordern — nur ein Hinweis, keine Garantie (frühere Eviction unter Last möglich). Eine Mindestlänge für cachebare Präfixe ist nicht dokumentiert (unbelegt).

## Migrations-Hinweise
- **VON Muse Spark 1.3 weg**: Knappheits-, Selbstprüfungs- und „erfinde nichts"-Instruktionen wieder ergänzen, wenn das Zielmodell diese Eigenschaften nicht von sich aus mitbringt; die `developer`-Nachricht auf `system` zurückdrehen, falls das Ziel keine Developer-Rolle kennt; Rückfrage-Verhalten neu regeln, weil Zielmodelle ohne „asks for input when needed" bei unterspezifizierten Prompts einfach raten — Defaults in den Prompt schreiben; Meta-spezifische Felder entfernen (`reasoning.summary`, `include: ["reasoning.encrypted_content"]`, `previous_response_id`) und den Konversationszustand clientseitig führen; Effort-Leiter neu kalibrieren, sobald das Ziel Reasoning abschalten kann oder andere Stufennamen führt; Audio-Pfade, die wegen der 1.3-Einschränkung auf Muse Spark 1.2 oder Muse Voice Transcribe ausgelagert waren, gegen die Fähigkeiten des Ziels neu bewerten.
- **ZU Muse Spark 1.3 migrieren**: `reasoning_effort: "none"` und jedes „denke nicht nach"-Äquivalent entfernen (HTTP 400) und auf `minimal`/`low` abbilden; Effort explizit setzen statt auf einen geerbten Default zu vertrauen; `tool_choice: "required"` bzw. benannte Tool-Erzwingung ausbauen (nur `"auto"` erlaubt, sonst HTTP 400) und den Zwang stattdessen sprachlich formulieren; `logprobs` entfernen (HTTP 400); Token-Budgets anheben, weil Reasoning-Tokens gegen `max_tokens`/`max_output_tokens` laufen; den System-Prompt in eine `developer`-Nachricht überführen; Verbosity- und Turn-Spar-Instruktionen aus 1.2-Prompts streichen; von Chat Completions auf die Responses API (bei Anthropic-Stack alternativ die Messages API mit `thinking`-Replay) wechseln, wenn Reasoning über Tool-Schleifen erhalten bleiben soll; Search Grounding erfordert die Responses API; den Prompt so umsortieren, dass Statisches vorn steht; `max` nur einplanen, wenn tatsächlich das Standard-Tier genutzt wird (Contributor kennt die Stufe nicht); Zugang selbst ist ein Base-URL-Wechsel — aus dem OpenAI-Ökosystem `api.meta.ai/v1` plus Key-Tausch, aus dem Anthropic-Ökosystem die Messages-API gegen `https://api.meta.ai`.
