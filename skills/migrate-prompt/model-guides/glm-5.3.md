# GLM-5.3

## Reasoning / Thinking
- Type: **forced on**. `thinking: {"type": "enabled"}` is the only permitted value — "Disabling reasoning is no longer supported". A request with `thinking.type: "disabled"` fails; on GLM-5.2/5.1/5/4.6 the model autonomously decides whether to think.
- Depth exclusively via `reasoning_effort`: `low` (mild inference, supported only on 5.3/5.3-Flash) | `high` (enhanced inference) | `max` (deep inference, documented as **"default and recommended"**). On the standard API endpoint, any other value of the platform-wide enum triggers an error ("Any other input will result in an error"); on the Coding Plan endpoint, `none`/`minimal`/`low` map to `low`, `medium`/`high` to `high`, and `xhigh`/`max` to `max`; in open weights, a missing or unrecognized value silently falls back to `max` ("defaults to max if not passed (or if set to any other value)"). On GLM-5.2, `none`/`minimal` (thinking off), `low`/`medium` (→ `high`), and `xhigh` (→ `max`) were still mapped.
- There is thus **no zero-thinking path**: "Thinking process will consume extra tokens, please manage your tokens." For workloads previously operating without thinking, recalculate token budgets; `low` is the floor, not "off". Whether reasoning tokens count against the same `max_tokens` as the response is stated by no Z.ai source (unbelegt).
- Reasoning output: Non-streaming as field `reasoning_content` alongside `content`; streaming as `delta.reasoning_content` first, followed by `delta.content`.
- `clear_thinking` discards the reasoning of prior turns. Preserved Thinking (`clear_thinking: false`) is disabled by default on the standard API endpoint, enabled by default on the Coding Plan endpoint; in the open-weights chat template, `clear_thinking` is set to `false` — for chat scenarios, the model card explicitly recommends passing `clear_thinking=true`. For coherent multi-turn runs, set to `false` and return historical `reasoning_content` unchanged — "All consecutive reasoning_content blocks must exactly match the original sequence", otherwise the caching advantage is lost.

## Prompting Style
- Z.ai positions 5.3 as a coding and agent model ("comprehensive advancements in complex software engineering and agent capabilities") — prompt directive and task-oriented, no role prose (unbelegt).
- Official task schema for agent prompts, four blocks: **Goal** (what is built/changed), **Context** (affected files, error messages, examples), **Constraints** (coding standards, architecture, security, dependency rules), **Done when** (acceptance criteria: tests pass, bug no longer reproducible).
- Clearly separate three context tiers: Task Context (the prompt), Project Context (repo structure + engineering rules), Environment Context (tools, permissions, runtime environment). Rule from documentation: "Put temporary instructions in the prompt, and put long-lived rules in project-level configuration files."
- Prepend a **planning phase** for complex tasks (explore codebase, establish scope, confirm approach), instead of immediately requesting code — immediate code requests lead to logic bugs and rework according to docs.
- Keep sessions lean: one session per task, truncate long sessions with summaries, handle branches in new sessions.
- Do **not adjust `temperature` and `top_p` simultaneously** — the migration page explicitly recommends tuning only one of the two values.
- A GLM-5.3-specific prompt engineering page does not exist; any stylistic assertion beyond this is unbelegt.

## Strengths & Weaknesses (prompt-relevant)
- Strengths: Agentic coding in realistic scenarios (+50% compared to GLM-5.2 on Z.ai Code Bench, Terminal-Bench 3.0 up from 4.6 to 28.3); emergent security/vulnerability capabilities (CyberGym 84.5%, ExploitBench 54.4%); higher token efficiency according to Z.ai (at max effort 34.5% at ~75K output tokens per task vs. 23.4% at 96K for GLM-5.2); 1M context and 128K output in one model; context caching with reported `cached_tokens`.
  - Base is the **same base model as GLM-5.2** according to the official model card ("same base model as GLM-5.2"); performance gains originate from post-training — prompt content carries over directly, only the thinking contract changes.
- Weaknesses: **Text-only** ("GLM-5.3 currently supports text-only inputs"), so no image input — visual capabilities are listed in release notes only for `glm-5.3-flash`; narrow `reasoning_effort` enum lacking `medium`/`xhigh`; ported effort values from other providers trigger an error on the standard API, but fall back silently to `max` in self-hosting (no error, highest cost); no published knowledge cutoff (unbelegt); as a third party, Mistral hosts the model unmodified as `zai-glm-5-3` (GA, according to Mistral global and EU, not yet via the US endpoint); other third-party clouds are not verified (unbelegt).
  - The migration page explicitly warns during migration against "excessive randomness or excessive conservatism" — cross-check sampling and response length after migration instead of carrying over old values.

## Output & Format Conventions
- 1,000,000 tokens context window, `max_tokens` up to 128K; input text, output text.
- Sampling defaults: `temperature` 1.0 (range 0.0–1.0), `top_p` 0.95 (range 0.01–1.0), `do_sample` `true`; `stop`: schema allows 4 entries, but according to parameter description currently only one stop word is supported ("Currently, only one stop word is supported").
- Structured Output via `response_format: {"type": "json_object"}` (default `"text"`); function calling via `tools` (max 128 functions), `tool_choice` exclusively `"auto"` ("only auto is supported") — forced or named tool selection is not available.
- Streaming tool calls requires `stream=true` **and** `tool_stream=true`; arguments arrive incrementally and must be reconstructed from `delta.tool_calls[*].function.arguments`.
- Price per MTok: Input $1.40, cached input $0.26, output $4.40; cached input storage currently free (as of 2026-10-13).
- Via Mistral's API (`zai-glm-5-3`), `message.content` always returns as a chunk list (thinking + text) regardless of `reasoning_effort` — there is no plain string mode there; `reasoning_effort` there is `low`/`high`/`max`, not `none`.
- Release notes entry: 2026-08-18. Model card: 753B parameters (architecture tag `glm_moe_dsa`; active parameters not specified, unbelegt).

## Migration Notes
- **MIGRATING FROM glm-5.3**: Target models without forced thinking require explicit thinking setup again (toggle, budget, or target effort field) — otherwise a 5.3 prompt runs there without reasoning; do not blindly carry over `reasoning_effort: max`, as other providers calibrate scales differently; remove or map `clear_thinking`, `tool_stream`, and `reasoning_content` handling to target conventions; re-add explicit verification and step-by-step instructions if the target does not reason deeply by default; check 1M context and 128K output assumptions against smaller target windows; replace `response_format: {"type": "json_object"}` with the target's structured output format.
- **MIGRATING TO glm-5.3**: (1) **Breaking**, official wording: "If your application currently uses `thinking.type: "disabled"`, please change it to `enabled` and set `reasoning_effort` to `low` before updating the model ID to `glm-5.3`. Otherwise, the request will fail." Every non-thinking fast path becomes `enabled` + `low`. (2) Remove `reasoning_effort` values from the GLM-5.2 era (`none`, `minimal`, `medium`, `xhigh`) — they were mapped there, but cause an error on the standard API here; in self-hosting there is no error, but a silent fallback to `max` — therefore never import `none`/`minimal` as "off", but explicitly set `low`. (3) Set `model` to `"glm-5.3"` and adapt `max_tokens` to the 128K limit. (4) Use `temperature` 1.0 / `top_p` 0.95 as baseline, subsequently tuning only one of the two values. (5) Convert streaming tool calls to `tool_stream=true` plus argument concatenation. (6) Extend multi-turn workflows with `reasoning_content` and set `clear_thinking=false` if the reasoning chain should persist across turns. (7) Multimodal routes fail — route image inputs to `glm-5.3-flash`, which has native visual capabilities according to release notes. (8) After migration, complete the official verification checklist: response quality, randomness/conservatism, tool streaming, plus latency and cost under long context and deep thinking. (9) Reduce multiple stop sequences to one; remove `tool_choice` values other than `auto` (a replacement for forced tool selection is not documented, unbelegt).
